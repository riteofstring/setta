## 2026-03-13 05:15:07 PDT

This change set resolves the app-generation regressions called out across the top-level reviews and simplifies the chat submission flow instead of adding more branching. The previous implementation had three separate problems that interacted badly: queued `/app-*` submits bypassed the canonical slash-command submit path, app-generation mode was not durable across normal follow-up or edit flows, and stale local-storage keys still influenced runtime behavior even though the UX had moved to a chat-first flow.

The frontend fix starts by making slash-command app-generation submits explicit. Built-in app-generation commands now resolve to a concrete submission with a prompt, attachments, and `appGeneration` metadata, and queued drafts replay that same submission path instead of replaying raw text. That removes the old split between immediate slash-command handling and queued replay, which was the main reason `/app-json` and `/app-image` could silently degrade into plain chat if they were sent while another response was active.

The next fix makes app-generation context real chat state. The AI store now tracks app-generation details per chat and per message, plus pending app-generation details for draft surfaces before a chat id exists. Project chat submit, follow-up, and branch-edit flows all read from that same source of truth, and optimistic updates carry the metadata forward immediately. When agent runs are refreshed, the store also rehydrates app-generation metadata from authoritative run inputs so the active mode survives hydration and refresh boundaries.

The local-storage cleanup removes the stale app-generation persistence keys from the frontend store and stops using hidden persisted values to influence runtime requests. Chat submits and edited-message submits now send deterministic `appSpecStreamingEnabled: false` payloads, and app-generation mode is carried only by the explicit per-submit metadata. This makes behavior visible in code and removes the hidden "depends on old browser state" failure mode.

The backend prompt and provenance path were also corrected. The `prompt_builder` system prompt no longer tells the model to use the removed App pane workflow, and app-generation metadata is now written into agent-run inputs so the frontend can recover it later without heuristics.

Before these fixes, user experience was inconsistent: an app-generation slash command could work on the first submit and then quietly stop behaving like app generation if it was queued, followed up with plain text, or edited into a branch. Developer experience was similarly poor because app-generation behavior was spread across slash-command execution, local storage, chat submit payload construction, and partially missing edit logic. After the refactor, the behavior is explicit and uniform: queued app-generation commands replay correctly, follow-up messages preserve the active app-generation mode, edits preserve the originating app-generation context, and the runtime no longer depends on stale local-storage leftovers.

Test coverage was added where the old gaps existed. Frontend unit and integration coverage now verifies queued slash-command replay, deterministic request payloads, removed local-storage keys, and edited-message preservation of app-generation metadata. Backend tests verify the prompt-builder wording and run-input provenance. Playwright coverage verifies slash-command payloads, follow-up preservation of active app-generation mode, and queued replay through the same path as immediate submission.

## 2026-03-13 06:31:24 PDT

This pass finishes the provenance fix and removes the remaining dual-path behavior instead of papering over it. The key structural change is that app-generation state is now represented as explicit per-message provenance, carried as `appGenerationByMessageId` from submit, to run inputs, to chat hydration, and back into the frontend store. That means the chat history itself defines where app-generation context applies, rather than whichever mode happened to be active most recently in the UI.

On the frontend, the app-generation helpers were reduced to a simpler model: a per-chat `activeAppGeneration` derived from message order plus an authoritative `appGenerationByMessageId` map. Submit, optimistic update, rollback, hydration, branch editing, and draft-surface seeding now all go through that same state shape. The important behavioral effect is that a follow-up in an app-generation thread preserves the prior context, while editing or redoing an older plain-chat message no longer inherits a later app-generation mode by accident.

The branch/edit path was cleaned up in particular. Edited-message submits now retain provenance only for the kept user messages in the new branch history, then overwrite the edited message with the explicit mode chosen for that edit. That removes the previous "fallback to latest active mode" behavior and makes branch behavior deterministic across reloads, hydration, and thread continuation. "Continue in new thread" now seeds both message history and app-generation provenance together, so the new draft thread starts from the same context as the source thread.

Slash commands were simplified in the same spirit. The composer now distinguishes between a command being handled and a command actually being submitted. Queued replay only removes a draft after a successful submit, which fixes the data-loss case where a queued `/app-*` command could disappear after a failed replay. Custom slash commands also now support explicit `appGenerationMode` metadata, so they use the same request contract as built-in app-generation commands instead of a weaker prompt-only path.

The backend contract was trimmed to match the real product. The chat route no longer accepts the retired `appSpecStreamingEnabled` flag or the removed chat-level reference-image override fields, and the app-generation prompt builder no longer mentions the old streaming/App-pane path. Instead, the backend normalizes the submitted provenance map to the retained user-message history, stores that map on the run, and returns it during chat hydration. This eliminates the old split between "current mode for the latest submit" and "best-effort reconstruction later from runs."

The UX before these changes was fragile in several distinct ways: queued slash commands could be lost, custom commands behaved differently from built-ins, old plain-chat messages could turn into app-generation edits, and a refreshed or continued thread could silently lose the originating mode. After the refactor, the behavior is consistent across immediate submit, queued replay, edit, redo, branch, hydration, and continuation. The DX improvement is similar: there is now one request/response contract, one provenance representation, and tests that cover the negative cases that were previously only described in review docs.

Verification was expanded at every layer. Frontend tests now cover hydrating provenance from chat responses, preserving plain-chat edits inside mixed-mode histories, and restoring queued slash-command drafts after replay failures. Backend tests cover authoritative provenance normalization and persistence for branch edits. Playwright coverage now asserts the per-message payload contract for built-in app-generation slash commands and verifies that custom slash commands with an explicit submission mode send the same kind of app-generation request. A CDP pass also confirmed the new submission-mode combobox renders correctly in the Project AI slash-command settings view at both full and narrower widths without clipping or overlap.

## 2026-03-13 07:24:52 PDT

This pass closes the remaining regressions identified in the top-level reviews and simplifies the chat submission contract instead of adding more fallback logic. The main correctness fix is that custom slash-command submission mode is now explicit end-to-end. Before this change, `Plain chat` and `inherit the active thread mode` both collapsed into the same falsy value, so a custom command saved as plain chat could still inherit an active app-generation thread and silently send the wrong payload. After the fix, the slash-command parser preserves explicit plain-chat intent, the composer forwards that as an explicit `appGeneration: null` override, and Project Chat only falls back to the active thread mode when no override exists at all.

The queued replay path was also reduced to a simpler and more accurate model. The previous implementation treated several slash-command outcomes as though they were successful submissions even when nothing had reached the backend, which is why queued drafts could disappear behind temporary "unavailable" or "reload authority first" feedback. The composer now uses explicit replay outcomes for real submit, terminal local handling, retry-later, and actual failure. That makes the queue behavior much easier to read in code and fixes the user-facing draft-loss bug without adding more hidden conditions.

Persisted app-generation provenance is now fully single-source. Run inputs no longer store legacy run-level `appGenerationMode` alongside `appGenerationByMessageId`, and backend/frontend hydration helpers now ignore legacy-only runs instead of reconstructing per-message provenance from them. The request-level `appGenerationMode` still exists for the live submit itself because the backend needs it to build the current system prompt, but persisted provenance now comes from one field only: `appGenerationByMessageId`.

Several nearby areas were tightened while making those fixes. Custom slash-command storage and normalization now use one explicit `AppGenerationMode | null` shape, the slash-command settings UI always renders the saved submission mode label including `Plain chat`, and the Project Chat submit-resolution rule now lives in a small focused helper instead of an inline null-coalescing expression that hid the bug. The resulting code is flatter and more obvious: fewer sentinel meanings, fewer ambiguous `null` cases, and less branching around replay.

The UX change is direct. Before this pass, the UI could promise `Plain chat` while still steering the model into app-generation behavior, and queued slash commands could vanish even though the user had only hit a temporary unavailable state. After the fix, saved commands truthfully show their submission mode, plain-chat custom commands stay plain even inside an active app-generation thread, and retry-later slash commands remain queued until the command is actually executable. The DX improvement mirrors that: one persisted provenance representation, one explicit submit-override rule, and one replay model that matches visible behavior.

Verification was extended specifically around those failure modes. Vitest coverage now asserts that custom plain-chat commands submit `appGeneration: null`, that Project Chat does not inherit the active mode when the override is explicitly null, and that queued unavailable or authority-refresh slash commands stay queued instead of being dropped. Backend tests now assert that legacy-only run inputs no longer reconstruct per-message provenance. Playwright coverage now includes the mixed-mode case from the reviews: start an app-generation thread, run a custom command configured as plain chat, and assert that the second `/api/getLLMResponse` payload clears `appGenerationMode` and does not assign new provenance for that user message. A CDP check also confirmed the Project AI slash-command settings UI renders a saved `Plain chat` row correctly at both desktop and narrower widths.

## 2026-03-13 08:02:12 PDT

This pass resolves the last two review blockers and removes the remaining dead provenance API instead of layering new exceptions on top of the existing flow. The first blocker was in the Project AI slash-command settings reducer: mode-only edits were treated as no-ops because the reducer only compared `command` and `prompt`. That meant the new submission-mode combobox looked live but silently discarded `JSON Render`, `Image to JSON Render`, `Prompt Builder`, and `MCP Server` selections unless some other field changed at the same time. The reducer now treats the draft as one full value object, including `appGenerationMode`, and only clears it when the entire draft returns to the empty default. That makes the UI behavior match the stored value and removes the hidden special case around mode-first edits.

The second blocker was the missing attachment invariant for image-guided app generation. `/app-image` and custom slash commands configured as `json_render_with_image` were allowed to submit without any image attachment even though their prompt contract explicitly says they should match an attached reference image. The fix is intentionally simple and mode-driven: if the resolved app-generation mode is `json_render_with_image`, both the frontend slash-command submit path and the backend `route_get_llm_response` path now require at least one image attachment. This applies equally to built-in slash commands, custom slash commands, queued replay, and direct API calls, so the rule no longer depends on which UI path happened to trigger the request.

The nearby cleanup was to finish converging on one provenance mutation path. The frontend still exported two test-only helpers that could mutate app-generation details without recomputing the active mode from message order. Those helpers were removed, and the tests were rewritten to use the same `setChatAppGenerationForMessage(...)` path as runtime code. That leaves a single readable contract for provenance writes and removes the easiest way to reintroduce state drift later.

The UX improvement is straightforward. Before this pass, the custom slash-command settings panel could claim that mode selection was available while actually saving plain chat, and image-guided generation could proceed without the image the UI had just told the user mattered. After the fix, the settings row truthfully shows the selected submission mode immediately after creation, and image-mode commands fail fast with actionable feedback instead of producing a misleading success path. The DX improvement is similar: one draft comparison rule, one image-mode invariant keyed off the authoritative app-generation mode, and one provenance write API instead of a split runtime/test surface.

Verification was added exactly where the regressions existed. Vitest now covers mode-only draft updates, mode-first custom-command drafts, built-in `/app-image` submit blocking without an image, custom image-mode slash-command blocking without an image, and the canonical provenance mutation flow after removing the redundant helpers. Backend tests now cover both the helper-level attachment rule and the real managed-chat route rejecting `json_render_with_image` without an image before any run starts. Playwright coverage now creates a custom slash command through the actual settings UI, verifies that the row renders `Submits as JSON Render.`, and confirms the emitted `/api/getLLMResponse` payload carries the selected mode. A second Playwright case verifies that `/app-image` does not submit anything until an image is attached. A CDP pass on the headed dev instance confirmed both visible behaviors directly: the authored custom command persisted and displayed `JSON Render`, and `/app-image` without attachments showed the attachment-required message with no chat submit request fired.
