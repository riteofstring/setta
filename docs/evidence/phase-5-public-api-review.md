# Phase 5 public API review

## Scope

This review covers the first Phase 5 hardening batch. It was performed on 2026-08-09 from the
built declaration closure generated by `corepack pnpm api:report`, the package manifest, packed-file
allowlist, unrelated consumer fixture, and package README.

The generated `.reports/public-api.md` is intentionally ephemeral. It records the exact declaration
closure for human review, but it is neither a compatibility promise nor a checked-in API snapshot.
Later pre-milestone API changes remain allowed when they simplify the permanent package boundary.

## Declared entry points

| Entry point                   | Reviewed ownership                                                                                                                      |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `@setta/workspace`            | Convenience union of the core and React entry points.                                                                                   |
| `@setta/workspace/core`       | Framework-neutral document, validation, traversal, policy, placement, item-tree planning, and immutable application contracts.          |
| `@setta/workspace/react`      | React rendering, section registration, workbench interaction, item-tree rendering, and host extension contracts.                        |
| `@setta/workspace/testing`    | Testing helpers plus deterministic Phase 0 geometry and adapter evidence; application runtime code does not depend on this entry point. |
| `@setta/workspace/styles.css` | Required package-owned CSS and scoped semantic theme tokens.                                                                            |

All targets stay inside `dist`. Package and consumer boundary checks reject source aliases,
undeclared subpaths, and direct imports of the emitted internal declaration-closure modules. The
root convenience surface deliberately re-exports both the `SortableItemTree` core model type and
React component value under TypeScript's separate type and value namespaces.

## Naming and ownership findings

- Runtime contracts consistently use workspace, section, and item terminology. XYFlow nodes and
  dnd-kit events remain adapter details and do not appear in the generated declaration closure.
- `WorkspaceDocument` is the serializable package model; `SectionDefinition` is the host renderer
  registry contract. Neither includes backend, persistence, Setta application, or compatibility
  fields.
- `ItemMovePlan` remains intentionally generic because hosts may use the sortable tree for fields,
  controls, parameters, or other item meanings. Section movement retains the distinct
  `SectionMovePlan` name.
- `WorkspaceInteractionBoundary` is the public opt-out surface for host content. Internal marker
  class names remain private.
- `createEmptyWorkspaceDocument` now preserves an explicitly supplied host payload type. The prior
  default-only return forced the React owner to cast an actually empty document and made controlled
  examples needlessly awkward. The generic change removes that cast without changing serialized
  output or adding a second document path.
- No additional rename or alias is warranted before the milestone. Adding compatibility aliases
  for speculative names would violate the greenfield boundary.

## Package and documentation findings

The private manifest now carries the plan's discoverable one-sentence package description while
remaining free of `publishConfig`, release automation, public licensing metadata, and registry
credentials. Generated declarations, source maps, the five declared entry points, required CSS,
README, and third-party notices remain covered by the exact tarball allowlist.

The package README now begins with local-install guidance, an entry-point map, a five-minute
uncontrolled example, and a controlled generic-document example before the detailed reference.
Both examples use only declared package exports. The README continues to state that payload
updates, persistence, ID allocation, renderer behavior, and domain policy belong to the host.
