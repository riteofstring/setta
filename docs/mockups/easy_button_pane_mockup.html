    Open questions

    • Rail lifetime. Does the NOW rail retain history across a whole session, or reset per request? Retaining it makes the pane accumulate a transcript by the back door — which is exactly what this pane exists to avoid. Reset-per-request is the honest reading of the spec, but then a long run's early context is unrecoverable. (This mockup resets per request, keeps ~6 entries visible, and hides both rail headers entirely until their rail has content — an empty rail labelled NOW is just noise in the state that most needs to be empty.)
    • Clarifying questions. If the AI needs to ask something mid-run, there is no transcript to put it in. Options: the button itself becomes the question (glyph swaps, question text under it, mic re-arms); a modal over the swirl; or a hard constraint that this pane never asks and instead makes an assumption and reports it as an artifact.
    • Artifact depth. Are artifacts click-through-able to a full detail view / the underlying run / a terminal? If yes, the pane leaks back into the transcript world. If no, artifacts must be genuinely self-sufficient, which raises the bar on their generation.
    • Mic interaction. Push-to-talk (hold the button) vs tap-to-toggle. Tap-to-toggle is shown here, but it needs a clear end-of-speech signal (silence timeout? explicit tap?). Mic permission also has to be requested somewhere — likely on first tap, with a denied-state fallback that points at the footer input.
    • Stop semantics. Tapping the button while working — does it cancel in-flight agents, pause them, or just detach the UI? With multiple agents this needs a real answer, including what happens to artifacts already emitted.
    • Left/right coupling. This mockup shows the request text (faintly) during Working. That is the user's own words, not AI transcript — but it's a judgment call worth confirming.

    Integration checklist

    Adding a real easy-button pane means touching, in order:

    1. internal/workspaceui/types.go — add SurfaceKindEasyButton const and include it in ContractValueSets().
    2. internal/workspaceui/store.go — add to validSurfaceKind(), or persistence rejects it as corrupt state.
    3. Regenerate contracts. Never hand-edit desktop/src/generated/backend.ts.
    4. workspace-layout/types.ts — add to productSurfaceKinds (a hand-maintained mirror; nothing ties it to the generated union, so it can silently drift).
    5. surface-adapters.ts — add a factory to defaultSurfaceAdapterFactories. Compiler-enforced.
    6. react-dom-surface-adapter.tsx — add a branch to the if-chain. This one is NOT compiler-checked — a missing branch is a runtime throw.
    7. runtime-policy.ts (surfaceRuntimeCategories), surface-dom-content.ts, benchmark-scene.ts. Compiler-enforced.
    8. pane-title-metadata.ts — icon. Silent fallback if missed.
    9. workspace-scene.ts — pane limit (likely 1).
    10. workspace-toolbar.tsx — toolbar button + shortcut, to make it openable.

    Runtime-policy note

    A perpetually-animating swirl interacts directly with the freeze/throttle policy in runtime-policy.ts. This pane most likely wants always-live while a request is in flight, but it must remain freezable when idle or offscreen — otherwise it burns GPU sitting in a background column. That means the runtime category can't be a static per-kind constant the way the existing kinds are; either the pane needs a dynamic category, or it needs to self-suspend its animations on freeze() and restart on resume().

    Also: the swirl here uses filter: blur() on a container whose children animate. Even though the filter value itself is static, the blur is re-evaluated every frame because the subtree repaints. For production, consider a pre-blurred sprite, a canvas/WebGL layer, or accepting softer conic stops with no blur at all. Worth measuring before committing — this pane is the whole screen.

    Full-width note

    There is no "full width" pane flag today. Horizontal size is a property of the column (ColumnWidthSpec), not the pane; vertical size is the pane's weight. So "opens at full width" means either giving it its own column at { unit: "proportion", value: 1 }, or reusing the maximized-pane path in layout-engine-base.ts. The two behave differently when the user then opens a second pane — the proportion column shrinks, the maximized pane doesn't. Pick deliberately.
