    Artifacts

    How to drive this mockup

    The pane carries four independent attributes, and the control rows above drive them separately. data-state is the run (idle, working, complete). data-capture is the microphone (off, requesting-permission, connecting, listening, committing, failed). data-speech is what the runtime can do, and data-playback is what is coming out of the speaker. The combination worth looking at is working + listening: a voice steer, with the swirl stepped back, the rings live, the new utterance bright, the Current focus faint beneath it, and Stop still reachable. A single enum could not express that, which is why the previous version of this mockup had no design for the plan's headline feature.

    data-focus is the narrator's projection of the objective: none before a run, current, updating while a revision is in flight after accepted steering, and stale when the narrator has died and the visible text may be out of date. Steer a live run — by voice, or by typing into the footer — and watch the focus hold its last good text under Updating focus… before the revision replaces it. The FOCUS row jumps straight to any of those states.

    The axes are independent in the DOM and emphatically not in the product, so a control the pane could not reach from where it is now is greyed out, with the reason on hover. A terminal status needs a run to be about; a degraded narrator can write no focus revision, so FOCUS collapses to Stale; the microphone rows need a runtime with voice configured; Committing needs an open microphone; No speech and Submit are failures of an utterance that already exists; and nothing can be spoken in idle, where there is neither a highlight nor a summary to read. Clicking TERMINAL during a run lands it that way — a live transition, which pulses and speaks by the rules above. Clicking it on a run that has already ended merely restates it, and does neither.

    Settled

    Answered by docs/plans/easy-button-speech-20260709.md; they used to be open questions here.

    • Mic interaction. Tap-to-toggle. The second tap is the end-of-speech signal — no silence timeout, no punctuation heuristic, and only the provider's completed transcript is eligible to submit. Escape cancels without submitting and gives the typed draft back. Permission is requested on first tap; denial points at the footer input and is not reported as a provider failure.
    • Stop semantics. The centre control never cancels the run. It is the recorder in every state: it starts a request from idle, steers from working, and starts a new request from complete. Cancelling the run belongs to the secondary Stop button, which is reserved in .action-slot in every state and stays live through a steering utterance — stopping a run must never require finishing a sentence first. Stopping does not discard the run: it ends it. The run becomes terminal with status stopped, keeps every artifact it already emitted, and shows its summary without a check mark.
    • Terminal status. Three of them, and the pane treats them differently, exactly as the shipped pane does. completed earns the green dot, the cyan border, the check mark, and the confirm pulse. failed earns the alarm colour on the border, the glyph, and the last highlight dot. stopped earns nothing — it rests, because a run the user cancelled did not go wrong, it was told to stop. Neither failed nor stopped pulses: a celebration would contradict the summary line sitting right below it.
    • The centre is Current focus, not the user's words. It begins as revision zero of the shared-normalized initial request and is then revised by the narrator as accepted steering changes the objective. It describes the goal and the constraints still in force — never recent activity, never a quotation — so it carries a standing CURRENT FOCUS label. It is never sent back to the working agent and is never spoken. Accepted steering shows Updating focus… over the last good text until the revision lands; there is no Steering: … echo, because the pane does not quote the user back and a timer-based confirmation would be a fact the renderer invented. A dead narrator leaves the focus stale: the instruction reached the agent, but the projection may be out of date.
    • NOW stays narrator-only. Raw typed or spoken steering never appears in the rail, never counts against highlight caps, and is never spoken. A focus revision is not a highlight. The full-fidelity user/agent record lives in the hidden chat conversation; a request-history surface is a separate feature.
    • Highlights and summaries are written to be read aloud. The narrator stays the sole author, and its prompt now requires short, grammatical, pronounceable text: no paths, no terse identifiers, no symbolic durations. The mechanical tail the service appends is human-readable prose (Done in 2 minutes 14 seconds with 3 artifacts.), so the one exact persisted string works for both the eye and the ear — including when a degraded narrator leaves the tail standing alone. No second model rewrites anything on its way to the speaker.
    • Terminal outcome never changes the glyph. While speech is configured the centre control stays a microphone in every state, including terminal ones, because it is still the recorder. Outcome is carried by border and rail tone, the summary's check mark, and the completion pulse — which is why the shipped pane's Check/X glyph swap does not survive into this design.
    • Speech output. Opt-in and device-local, initially off. Only live events speak; a restored snapshot, or a jump straight to a terminal state, never replays its history. Automatic final speech fires for completed and failed but never for stopped — you just pressed Stop, and a pane that then talks at you is ignoring the instruction you gave it, while an unattended run going wrong is most of why voice output exists at all. Replay stays available for all three, whenever voice is configured, even with automatic playback off. The AI-voice disclosure lives in the output menu, because OpenAI policy requires it wherever the voice can be enabled.

    Deltas from the previous mockup

    The pixel-match stills move. These moves are deliberate:

    1. The working-state centre glyph was a stop square. It is now the mic — the centre control is the recorder, not the stop button.
    2. .action-slot is reserved in every state (34px, plus a 14px margin), which grows the stage in all three captured stills. This brings the mockup toward the shipped pane, which already reserves it. The mockup was the one that was wrong.
    3. The complete-state summary row gained the replay control.
    4. .transcript is gone. The centre no longer holds an immutable copy of the initial request. It holds .focus-block — a .focus-label plus .current-focus — and the caret lives on .capture-line, since a narrator projection is not something anyone is typing. .steer-note and data-steer are deleted outright. The pixel-match probe's requestText component must be repointed at .current-focus, and given the new actionSlot, stopButton, captureLine, and focusLabel spellings.
    5. .capture-line is display: none — not a zero-height box, because a flex gap still spaces an empty child — so the caption slot keeps its 66px in every state where the microphone is closed. Only active capture grows it.
    6. The summary is the narrator's, not a stat line. The persisted EasyRun.Summary is one or two plain-language narrator sentences answering what happened or what was produced, followed by the service's human-readable mechanical sentence (Done in 2 minutes 14 seconds with 3 artifacts.). The narrator is explicitly forbidden from mentioning commands, file paths, tool calls, or agent mechanics, and forbidden from inventing those facts. The mechanical sentence stands alone when narration is degraded, so the same exact persisted string remains useful to both the eye and the ear.
    7. Narrator health is now an axis. data-narrator is ok | degraded. Degraded means the narrator died while the run lived: highlights stop arriving, the summary collapses to its mechanical tail, and the pane prints narration degraded — a separate line, in a separate colour, from the amber Voice failed. Three systems, three failures, three lines. The summary also scrolls inside a bounded box now, and is not rendered at all outside complete, both as the shipped pane does.
    8. The listening field converges, and is soft. The rings used to expand outward from the button, which is the universal sign for emitting — a ping, a transmit, a loudspeaker. An open microphone is doing the opposite. They now start wide, fade in, accelerate inward, and are absorbed at the button's rim. They are also no longer 1px strokes: crisp rings cut across the live transcript a few pixels below and pulled the eye off the words being captured. They are built the way the swirl is now — a static blur on the container, gradients on the children — so the two motions belong to the same pane.
    9. Speech points at its source, and the source follows the run. The highlight being read turns its own dot into a small teal equalizer and lifts its text to full foreground; the summary gets the same equalizer inline before the ✓, and the same lift. Which one is read is not a preference: highlights are spoken live while the run works, the summary is spoken when the run lands, and nothing else exists to be read. outputMode decides whether speech happens at all, never what is spoken — deriving the source from it produced a completed run pointing at a highlight, and a working run pointing at a summary it did not have. The bars sit absolutely inside the dot's unchanged 6×6 box, because growing the box would change the rail's height and justify-content: safe center would re-centre every row the moment speech began.
    10. Terminal status is now an axis. The old mockup had one terminal state and it was always a success. It now carries data-status (none | completed | failed | stopped), which drives the check mark, the border and glyph tone, the last highlight's dot, the confirm pulse, and whether the summary is spoken. Stop no longer returns the pane to idle: it ends the run as stopped and keeps the artifacts already emitted, which is what the shipped pane does and what the old "Stop semantics" open question was asking about.
    11. The button was off-centre. .pane-body used minmax(240px, 300px) 1fr minmax(280px, 380px). Unequal rails put the middle column's midpoint 40px to the left of the pane's, so the button, the caption, and the whole stage were off-centre by half the rails' 80px difference. The tracks are now equal — minmax(260px, 340px) on both sides — which centres the stage at every width with no magic offset. Both clamps preserve the old rail budget exactly (240 + 280 and 300 + 380 each still sum the same), so the middle column, and with it the 460px caption slot, is unchanged. Only the split between the two rails moved: the notes rail gains 40px and the artifacts rail gives up 40px.

    Follow-ups, not done here. The shipped pane copies the off-centre grid verbatim (easy-button.css), so it is off-centre by the same 40px and needs the same fix. easy-button-pixel-match-probe.js should gain actionSlot and stopButton components, now that both spellings exist — and its railLeft / railRight width comparisons will flag until the pane's grid is squared up.

    Open questions

    • Rail lifetime. Does the NOW rail retain history across a whole session, or reset per request? Retaining it makes the pane accumulate a transcript by the back door — which is exactly what this pane exists to avoid. Reset-per-request is the honest reading of the spec, but then a long run's early context is unrecoverable. (This mockup resets per request, keeps ~6 entries visible, and hides both rail headers entirely until their rail has content — an empty rail labelled NOW is just noise in the state that most needs to be empty.)
    • Clarifying questions. If the AI needs to ask something mid-run, there is no transcript to put it in. Options: the button itself becomes the question (glyph swaps, question text under it, mic re-arms); a modal over the swirl; or a hard constraint that this pane never asks and instead makes an assumption and reports it as an artifact.
    • Artifact depth. Are artifacts click-through-able to a full detail view / the underlying run / a terminal? If yes, the pane leaks back into the transcript world. If no, artifacts must be genuinely self-sufficient, which raises the bar on their generation.
    • Focus revision cadence. An accepted steer revises focus immediately. Ordinary progress may revise it only when a requested subgoal demonstrably finished and another became active — otherwise the narrator must return the previous focus verbatim. That rule is easy to state and hard to hold: a model with a revision slot available will want to fill it. Worth watching in the live evaluation.

    Integration checklist

    Adding a real easy-button pane means touching, in order:

    1. internal/workspaceui/types.go — add SurfaceKindEasyButton const and include it in ContractValueSets().
    2. internal/workspaceui/store.go — add to validSurfaceKind(), or persistence rejects it as corrupt state.
    3. Regenerate contracts. Never hand-edit desktop/src/generated/backend.ts.
    4. workspace-layout/types.ts — add to productSurfaceKinds (a hand-maintained mirror; nothing ties it to the generated union, so it can silently drift).
    5. surface-adapters.ts — add a factory to defaultSurfaceAdapterFactories. Compiler-enforced.
    6. react-dom-surface-adapter.tsx — add a branch to the if-chain. This one is NOT compiler-checked — a missing branch is a runtime throw.
    7. runtime-policy.ts (surfaceRuntimeCategories), surface-dom-content.ts, benchmark-scene.ts. Compiler-enforced.
    8. pane-title-metadata.ts — icon. Silent fallback if missed.
    9. workspace-scene.ts — pane limit (likely 1).
    10. workspace-toolbar.tsx — toolbar button + shortcut, to make it openable.

    Runtime-policy note

    A perpetually-animating swirl interacts directly with the freeze/throttle policy in runtime-policy.ts. This pane most likely wants always-live while a request is in flight, but it must remain freezable when idle or offscreen — otherwise it burns GPU sitting in a background column. That means the runtime category can't be a static per-kind constant the way the existing kinds are; either the pane needs a dynamic category, or it needs to self-suspend its animations on freeze() and restart on resume().

    Also: the swirl here uses filter: blur() on a container whose children animate. Even though the filter value itself is static, the blur is re-evaluated every frame because the subtree repaints. For production, consider a pre-blurred sprite, a canvas/WebGL layer, or accepting softer conic stops with no blur at all. Worth measuring before committing — this pane is the whole screen.

    Full-width note

    There is no "full width" pane flag today. Horizontal size is a property of the column (ColumnWidthSpec), not the pane; vertical size is the pane's weight. So "opens at full width" means either giving it its own column at { unit: "proportion", value: 1 }, or reusing the maximized-pane path in layout-engine-base.ts. The two behave differently when the user then opens a second pane — the proportion column shrinks, the maximized pane doesn't. Pick deliberately.
