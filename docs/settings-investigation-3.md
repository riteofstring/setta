# Settings Flicker Findings

- Prior mitigations still ensure the final settings value is correct: edits route through `SettingsProjectManager`, the change is saved immediately, and the websocket rebroadcast eventually aligns the UI with disk.
- Backend instrumentation confirms every `/settings` param edit continues to hit the settings manager—even after navigating away and back—so the earlier “wrong manager” theory is ruled out (`docs/backend_logs.txt:1`, `docs/backend_logs.txt:20`).
- When switching from lines back to dots, the server saves and rebroadcasts the new value (`docs/backend_logs.txt:22-24`), and the frontend receives the matching op-completed update (`docs/frontend_logs.txt:98-102`).
- Seconds later the backend emits an `update_and_broadcast_project_state` carrying the stale `"lines"` value with empty pending/completed op lists (`docs/backend_logs.txt:25`), which matches the transient `UpdateFrontendProjectState` that flips the UI back to lines (`docs/frontend_logs.txt:104-107`); a subsequent settings broadcast restores `dots` (`docs/frontend_logs.txt:115-123`).
- That orphaned stale broadcast is the likely source of the flicker. Next step is to instrument all callers of `BaseProjectManager.update_and_broadcast_project_state` to capture stacks/metadata when both op lists are empty so we can identify which code path emits the stale payload.
- Added critical logging in `backend/setta/project_state/base_project_manager.py` to dump call stacks whenever the broadcast fires with empty op lists so the next run should tell us which path issues the stale payload.
- New logs show those empty-op broadcasts come from `SettingsProjectManager.load_json_sources` (triggered via the JSON source file watcher). The stack traces point to the watcher-driven reload path as the author of the stale `"lines"` payload. Next step is to log the watcher event type and JSON contents so we can see whether the first reload is serving old on-disk data or if the merge logic regresses the value.
- Fresh logs confirm the first `load_json_sources` pass after a settings change is kicked off by `watch_json_source_files` before the file watcher refreshes the cached JSON; it replays the stale `self.json_sources` snapshot (still `"lines"`) and immediately reverts the UI. A subsequent watcher event reads the updated file (`"dots"`) and corrects the state, creating the flicker.
- Added `_refresh_and_load_json_sources` in `backend/setta/project_state/jsonSource/jsonSource.py` so watcher-triggered reloads now reread each affected JSON file from disk, rebuild the in-memory cache, and then merge into project state. This keeps `self.json_sources` synced and prevents the stale `"lines"` payload from ever being broadcast.
- The new “with_fix” logs (`docs/backend_logs_with_fix.txt`, `docs/frontend_logs_with_fix.txt`) show `JSONSource.preload_from_disk` and the subsequent `UpdateFrontendProjectState` both reporting `"dots"`; the UI no longer flashes the previous value when returning to `/settings`.
