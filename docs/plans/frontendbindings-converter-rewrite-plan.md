# Frontendbindings Converter Rewrite Plan

## Goal
Rewrite `internal/frontendbindings/converter.go` from scratch so the frontend
type generation pipeline looks like a Go-owned analogue of the main branch's
`frontend/generation/convert_pydantic_to_js.py` plus
`frontend/generation/convert_endpoints.py`.

The target outcome is:
- a generic Go type-to-TypeScript compiler
- a small Go-owned metadata layer for the cases reflection cannot express alone
- a separate endpoint-generation path
- no giant handwritten per-type TypeScript inventory inside the converter

Zod is optional. The rewrite should not depend on Zod. If it becomes useful, it
should come from the same intermediate representation rather than drive the
architecture.

## Why Rewrite Instead Of Incremental Cleanup
`internal/frontendbindings/converter.go` is still acting as a second
handwritten TypeScript implementation instead of a converter.

Current problems:
- it still contains a giant `manualTypes` inventory keyed by `reflect.Type`
- it still contains a large handwritten enum inventory
- it still mixes generic conversion, special-case type modeling, TS literal
  rendering, default materialization, and factory generation in one file
- each cleanup commit removes some local duplication, but the core shape stays
  the same

The file is too structurally wrong for piecemeal cleanup to converge quickly.
The faster path is to replace the architecture.

## Main-Branch Inspiration
The main branch frontend TS surface was mostly generated by:
- `frontend/generation/convert_pydantic_to_js.py`
- `frontend/generation/convert_endpoints.py`

The important design ideas to keep are:
- generic schema conversion is separate from endpoint conversion
- recursive dependency discovery is built into the converter
- the converter works from authoritative type information instead of from a
  giant handwritten TS inventory

The important thing not to copy is Python ownership. On this branch, Go owns
the contracts, so the equivalent design is:
- Go reflection and Go-owned metadata instead of Python Pydantic metadata
- Go endpoint specs instead of FastAPI route introspection

## Scope

### In Scope
- replacing `internal/frontendbindings/converter.go`
- introducing new files under `internal/frontendbindings/` to hold the new
  compiler, metadata, and default/factory generation helpers
- keeping `internal/frontendbindings/render.go` as the rendering layer unless a
  small adjustment is needed
- preserving `CurrentEndpoints()`, `CurrentRouteGroups()`, and route rendering
  as a separate concern
- moving converter special cases into a narrow, explicit Go-owned metadata
  layer

### Out Of Scope
- moving frontend endpoint ownership away from `internal/frontendbindings/specs.go`
- reintroducing Python as a source of truth for frontend contracts
- requiring Zod output
- preserving the current `converter.go` helper structure if it blocks a simpler
  design

## Design Principles
- Go is authoritative for contracts, defaults, and correctness-sensitive
  semantics.
- Generic discovery and compilation should be the default path.
- Reflection should handle ordinary structs, aliases, maps, slices, pointers,
  and enums.
- Special cases should be represented as metadata, not as ad hoc handwritten TS
  bodies scattered through the converter.
- Endpoint generation should stay separate from type generation.
- The remaining handwritten metadata should be narrow enough that adding a new
  normal owner type does not require editing a giant switch or map.

## Target Architecture

### 1. Discovery
Build a root type set from:
- `CurrentAdditionalTypeRoots()`
- endpoint request and response types from `CurrentEndpoints()`
- any narrow extra roots required by support declarations

This should remain broad and deterministic. The compiler should discover
dependencies recursively from those roots.

### 2. Intermediate Representation
Keep or replace `TypeDeclaration`, but the IR should remain simple and renderer-
friendly:
- object declarations
- alias declarations
- enum declarations
- local alias declarations
- set declarations
- type guards
- function declarations
- const declarations

The critical change is where the IR comes from. Most IR should be compiled from
Go types plus metadata, not handwritten one type at a time.

### 3. Generic Go Type Compiler
Introduce a new compiler that does the Go equivalent of
`convert_pydantic_to_js.py`:
- compile primitives, pointers, slices, arrays, maps, structs, and named types
- recursively emit dependent declarations
- treat string enums through a generic enum discovery path
- use wrapper override registries only to redirect ownership, not to restate TS
  structure

This should be the default path for most shared types.

### 4. Metadata Layer For Non-Reflectable Semantics
Reflection alone will not cover everything. Keep a narrow metadata layer for:
- named tuple aliases such as canvas point or transform tuples
- union membership declarations
- set and type-guard declarations
- property-level TS type overrides where the Go field type is intentionally too
  broad
- default providers for frontend creation helpers
- creation-time expression hooks such as generated ids or random names

This metadata must be Go-owned and minimal. The metadata should describe the
exception, not restate the whole object shape.

### 5. Default And Factory Generation
Replace the current handwritten factory bodies with a metadata-driven factory
generator.

The factory generator should support:
- plain merge-with-defaults creation from Go-owned default values
- nested default creation for composite types when needed
- narrow override hooks for creation-time expressions such as artifact id
  factories
- union discriminator helpers when a discriminator cannot be inferred from the
  ordinary create path

The generator should not require per-type handwritten field lists for ordinary
cases. If a field must be overridden, the metadata should name only the field
and the override reason.

### 6. Rendering
Keep `internal/frontendbindings/render.go` focused on:
- validating declarations
- rendering `generatedRoutes.ts`
- rendering `generatedTypes.ts`
- rendering `generatedEndpoints.ts`

If possible, `render.go` should not know whether a declaration came from pure
reflection or metadata.

### 7. Endpoint Generation
Keep endpoint generation conceptually aligned with main's
`convert_endpoints.py`:
- endpoint route specs stay explicit
- endpoint parameter and response type references come from the type compiler
- type conversion for endpoint payloads stays separate from route string
  generation

The rewrite should not pull endpoint logic back into the converter.

## Proposed File Layout
The exact names can change, but the responsibilities should be split roughly
like this:
- `internal/frontendbindings/type_declarations.go`
- `internal/frontendbindings/type_compiler.go`
- `internal/frontendbindings/type_metadata.go`
- `internal/frontendbindings/type_defaults.go`
- `internal/frontendbindings/type_factories.go`
- `internal/frontendbindings/render.go`
- `internal/frontendbindings/specs.go`

`converter.go` should be deleted at the end, not merely shrunk and renamed into
another monolith.

## Migration Plan

### Phase 0: Baseline And Freeze
- Document the current responsibilities of `converter.go`.
- Identify the families that still require special handling:
  - unions
  - tuple aliases
  - type sets and type guards
  - creation helpers with non-literal runtime hooks
- Treat the current converter as a reference implementation only while the new
  compiler is being built.

### Phase 1: Introduce The New Compiler Skeleton
- Add the new compiler files beside the existing converter.
- Reuse the current renderer and declaration validation.
- Define the metadata structures up front so special cases do not leak back
  into handwritten TS builder logic.

### Phase 2: Move Ordinary Types To The Generic Path
- Compile ordinary named structs, aliases, maps, slices, pointers, and enums
  through the new compiler.
- Route endpoint request and response types through the new compiler.
- Keep only the genuinely special families on the old path.

Completion bar for this phase:
- adding a new ordinary backend owner type should not require editing a
  handwritten TS declaration map

### Phase 3: Replace The Giant Manual Inventories
- Eliminate `manualTypes`
- eliminate the handwritten declaration inventories keyed by `reflect.Type`
- eliminate handwritten per-type create helpers for ordinary section and code
  object families

For section and code-object creation helpers:
- derive defaults from Go-owned default providers
- derive common fields from reflected property metadata
- use narrow metadata for discriminator and runtime hook exceptions

### Phase 4: Move Special Cases To Metadata
- Replace ad hoc special-case switches with declarative metadata entries
- keep only metadata that reflection genuinely cannot express
- make special-case metadata auditable in one place

Completion bar for this phase:
- special-case entries describe exceptions only
- no special-case entry restates an entire normal object declaration field by
  field

### Phase 5: Switch Rendering To The New Compiler
- Change `Build()` to use the new compiler
- delete the old converter path
- update focused tests to assert the new metadata-driven behavior instead of the
  old helper shape

### Phase 6: Cleanup
- delete `internal/frontendbindings/converter.go`
- remove dead tests that only pinned old converter helper shapes
- remove dead helper functions that existed only to support the old converter

## Testing Strategy

### Required Verification
- `./scripts/go.sh test ./internal/frontendbindings -count=1`
- `./scripts/go.sh test ./internal/pythonsharedtypes ./internal/pythonsdkcontracts -count=1`
- regenerate frontend bindings before finishing
- run `./gcf.sh` before landing the rewrite

### Test Focus
Prefer focused semantic tests over drift tests:
- representative plain struct conversion
- representative enum conversion
- representative union generation
- representative type-set and type-guard generation
- representative section or code-object creation helper generation from Go
  defaults
- representative creation helper with a runtime hook such as generated ids or
  random names

Do not add tests that merely rerun generators and diff checked-in artifacts.

## Zod
Zod is optional.

Acceptable approaches:
- no Zod output at all
- a later sidecar Zod emitter from the same IR
- a dual TS-plus-Zod emitter if it materially simplifies validation and does
  not distort the architecture

Unacceptable approach:
- letting Zod schema generation become the new source of truth

## Risks
- replacing the old converter too abruptly could break subtle frontend create
  helper semantics
- the metadata layer could regrow into a second manual schema system if it is
  not kept narrow
- tuple aliases and discriminated unions are the most likely places to leak
  special cases back into handwritten logic

## Success Criteria
- `internal/frontendbindings/converter.go` is deleted
- ordinary Go-owned types are converted without per-type handwritten TS
  declaration entries
- section and code-object creation helpers are derived from Go defaults and
  narrow metadata instead of handwritten field inventories
- endpoint generation remains separate from type generation
- adding a normal new owner type does not require editing a giant converter map
- the remaining metadata is small, explicit, and clearly about exceptions
