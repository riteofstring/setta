# Backend Capability Coverage Checklist

Snapshot date: 2026-03-14.

Primary agent entrypoint: `docs/plans/go-backend-rewrite/CURRENT.md`.

Companion caller-backed checklist:
`docs/plans/go-backend-rewrite/caller-backed-backend-surface-checklist.md`.

Audit/maintenance plan:
`docs/plans/go-backend-rewrite/backend-capability-coverage-checklist-audit-plan.md`.

Use this checklist to answer:
"Where does backend capability ownership live in the repo?"

Use the caller-backed checklist when the question is whether the current caller
already reaches Go transport today.

This doc is about runtime/service ownership, not current-caller reachability.
Archived dead history, vendor payloads, and third-party provider internals are
out of scope except where they are an explicit runtime boundary.

Together with the caller-backed checklist, this doc is the rewrite progress
tracker. File deletion is not the tracker while Python source is being retained
for mergeability.

Status meanings:

- `Go-owned`: Go owns the active runtime/service implementation for this
  capability area.
- `Shared boundary`: Go owns the main implementation, but Python and/or an
  external runtime still participates by design.
- `Python-owned`: the active implementation still lives under `backend/setta`.
- `Missing`: the capability is still required for product parity, but the
  rewrite currently has no acceptable Go-owned replacement.
- `Deferred`: the capability is intentionally outside the current rewrite
  scope.
- `External`: the capability depends on non-Setta providers, processes, or OS
  services rather than a Setta-owned implementation.
