**Observations**  
- Backend chat orchestration is hard-wired to Anthropics: `backend/setta/mcp/chat_manager.py:4-219` instantiates `AsyncAnthropic`, stores Anthropics `ContentBlock` objects, and assumes Anthropics stream events; persistence (`backend/setta/types/chat_messages.py:5-34`) and tests (`tests/project_state/chats/test_chats.py:6-55`) also import `anthropic.types`, so every stored chat is provider-specific.  
- The MCP client/server pair is thin: `backend/setta/mcp/client.py:5-150` still talks SSE directly, exposes only two tools (`backend/setta/mcp/tools.py:8-33`), and the only editing pathway is the ad-hoc string replace helper (`backend/setta/mcp/str_replace_editor_tool_fns.py:1-164`). Frontend “tools” like `startStreamingInto`/`stopStreamingInto` (`frontend/src/state/actions/ai.ts:385-520`) exist only for UI bookkeeping and aren’t executable by the LLM, so accurate project edits are mostly manual.  
- API key management is limited to two hard-coded providers: backend writes `.env` blindly (`backend/setta/routers/ai.py:85-128`), `frontend/src/utils/constants.ts:57-104` hard-codes `MODEL_GROUPS`, and the Project AI settings panel (`frontend/src/components/Panes/Overview/ProjectLevelAI/ProjectLLMSettings.tsx:6-48`) is just a pair of password fields without key validation, secret scoping, or UI to manage Portkey routes.  
- Streaming UX mirrors Anthropics wire protocol: `frontend/src/state/actions/ai.ts:101-334` handles `message_start`, `content_block_delta`, etc., `frontend/src/state/actions/websocketReceive.ts:120-152` forwards those unchanged, and `ProjectChatCore` renders tool calls and the “streaming into section” experience based on Anthropics tool naming conventions. Porting to another provider means rewriting this entire contract.  
- Server startup (`backend/setta/server_state.py:31-79`) eagerly spins up the MCP SSE transport and websocket broadcasts, so swapping in a Portkey gateway or plugging in other transports can’t happen without touching global state initialization.

**Plan**  
- Rebuild the backend foundations around provider-agnostic models and Portkey: remove Anthropics from `pyproject.toml` plus `backend/setta/mcp` & `tests/project_state/chats`, introduce a `backend/setta/llm/` package that defines internal message/tool dataclasses, serialization helpers, and storage format; migrate `DBE` chat persistence (`backend/setta/database/db_objs.py`) so old Anthropics transcripts can either be dropped or upgraded via a one-time converter.  
- Implement a Portkey-backed chat gateway: create a `PortkeyClient` wrapper (env-driven for API key + route) with streaming generators, map Portkey events to the new internal `LLMStreamChunk` types, and refactor `ChatManager` (or replace it with `ConversationService`) to run the call loop, enforce `deepThink`/system prompts, and forward streaming text + tool-call deltas over `WMHFrontendSender`. This includes updating `backend/setta/routers/ai.py` to use the new service, shrinking background-task glue, and letting models be dynamic (Portkey “route” names instead of the hard-coded `MODEL_GROUPS`).  
- Overhaul MCP/tool execution so the LLM can accurately modify Setta projects: replace the minimal `backend/setta/mcp` package with a “tool runtime” that exposes real project operations (read/write files in `setta_files/`, mutate section variants via the existing project managers, inspect terminals, run code generators). Each tool should have proper schema + docstrings via the existing `setta_tool` decorator, and the MCP client must support streaming tool output/status so Portkey can surface tool-call deltas; retire the Anthropic-specific string-replace shortcut once equivalent tooling exists.  
- Redesign the frontend chat stack to match the new backend contract: update `useAIStore` and `state/actions/ai.ts` to store provider-agnostic `LLMMessage` objects, refresh the websocket handler (`receiveLLMResponseChunk`) to handle the new chunk types (text delta, tool-call start/delta/stop, tool-result, stream-complete), and adapt `ProjectChatCore` to render streaming tool progress and file-edit previews using whatever metadata the new tools emit.  
- Build a robust API-key and Portkey-route management experience: add backend endpoints to read/write encrypted keys (or keep `.env` writes but expose validation + masking), surface available Portkey routes/models over HTTP, and expand the Overview “AI Settings” pane into a full form with add/remove/test actions, provider labels, and per-key status; wire this UI to watchers so `useAIStore` reflects external edits automatically.  
- Finish with validation + docs: extend unit tests under `tests/` to cover chat persistence, MCP tool contracts, and the new Portkey streaming parser; document the configuration flow (Portkey account, route IDs, env vars) in `docs/` or `README.md`, and add manual verification steps (e.g., run `source activate.sh && python -m unittest discover tests`, `pnpm start` to exercise streaming) so future contributors can reproduce the setup.
