# Branch Intent Summary

Compared against `go-rewrite`, using:
`git diff --name-status go-rewrite...HEAD`
and
`git diff $(git merge-base go-rewrite HEAD)..HEAD`

This branch is primarily an app-subsystem extraction and boundary-hardening branch. The dominant intent is to stop treating app mode as a host-owned built-in and instead treat it as a plugin-selected subsystem whose backend, frontend, deployment runtime, chat modes, MCP tools, and UI settings are all contributed through an explicit provider boundary.

## Features

**1. App subsystem backend ownership moved from host-owned built-ins to a plugin-selected provider boundary**
What changed: before this branch, the host directly owned app-definition routes, app deployment routes, app-generation chat mode behavior, app MCP tools, and app UI-setting entries. After this branch, those surfaces are built through `internal/appsubsystem` from the currently selected app-subsystem provider's declared capabilities, and the host only exposes them when a single valid provider is active.
Why this appears intentional: the change is systematic across HTTP, MCP, UI settings, deployment runtime registration, startup, chat-mode resolution, generated contracts, and tests. Old host-owned app definition handlers were deleted while new provider-oriented builders and tests were added.
Files/endpoints/components involved: `internal/appsubsystem/provider.go`, `internal/appsubsystem/appdefinitionhttp/routes.go`, `internal/appsubsystem/appdeploymenthttp/deployment_routes.go`, `internal/appsubsystem/appdeploymenthttp/ide_routes.go`, `internal/appsubsystem/mcptools/registrations.go`, `internal/appsubsystem/appuisettings/entries.go`, `internal/appsubsystem/chatmodes/chat_mode_contributions.go`, `internal/httpapi/frontend_route_registrations.go`, `internal/mcpx/server.go`, `internal/app/deployment_type_registry.go`, `internal/appsubsystem/deployment_runtime.go`. App HTTP routes now flow through provider registrations for `/getAppCatalog`, `/getAppDefinition`, `/validateAppDefinition`, `/setAppDefinition`, `/app/deployments`, `/app/deployments/{deploymentName}/versions`, `/app/deployments/{deploymentName}/latest`, `/app/deployments/current/session`, `/app/deployments/{deploymentName}/{version}/state`, and `/app/deployments/{deploymentName}/{version}/project_config`.
Default-value changes, moved/renamed UX flows, or relocated logic: app-generation skill routes are no longer unconditional host routes; share deployment IDE routes remain host-owned while app deployment routes are provider-contributed; app-related MCP tools and scoped UI settings are contributed instead of hardcoded into the default host registry.
Reviewer guardrail: do not move app subsystem routes/tools/settings/chat modes back into unconditional host-owned code unless a new architecture decision is made. Follow-up branches should preserve provider-gated registration and should not assume app mode exists independently of plugin runtime state.

**2. App-definition persistence became plugin-namespaced and app-spec files moved under the provider's storage root**
What changed: before this branch, app-definition data lived as top-level project-state data and app-spec persistence was effectively host-owned. After this branch, app-definition JSON is stored in `projectstate.Document.PluginData[pluginID]`, and the default app-spec file path is provider-scoped under `plugins/<pluginID>/app_specs/app.json`.
Why this appears intentional: the top-level `Document.AppDefinition` field and related projectstate app-definition helpers were removed, replaced by `PluginData`, new raw-JSON helpers, plugin-scoped app-definition normalization/compare-and-set services, and a new persisted-mutation path that coordinates document writes and external app-spec file writes.
Files/endpoints/components involved: `internal/projectstate/document.go`, `internal/projectstate/persisted_mutation.go`, `internal/projectstate/raw_json_object.go`, `internal/projectstate/frontend_source.go`, `internal/appsubsystem/appdefinition/service.go`, `internal/appsubsystem/appdefinition/document_storage.go`, `internal/appsubsystem/appdefinition/compare_and_set.go`, `internal/appsubsystem/appdefinition/normalize.go`, `internal/appsubsystem/appspec/store.go`, `internal/appsubsystem/appdefinition/backend_runtime.go`. Frontend and tests now expect paths like `plugins/setta-json-render-app-gen/app_specs/app.json`.
Default-value changes, moved/renamed UX flows, or relocated logic: app-definition types moved out of `internal/projectstate` into `internal/appsubsystem/appdefinition`; default app-spec path is no longer a generic host path and is now computed from the provider plugin ID.
Reviewer guardrail: do not "simplify" this back to a top-level `appDefinition` document field or a shared `app_specs/...` root. The plugin namespace is now part of the intended storage contract and follow-up reviews should preserve provider-specific paths and data ownership.

**3. Frontend app surfaces are now rendered through plugin registrations instead of host-owned components**
What changed: before this branch, the host frontend directly rendered the app route, overview app tab, preview surface, publish-app modal, and app slash-command set via host source files. After this branch, the host loads an app-subsystem frontend registration from the selected plugin and renders those surfaces through `AppSubsystemRendererHost` and an explicit frontend host API.
Why this appears intentional: the host app components were deleted or reduced to runtime shells while a full plugin frontend package, runtime registration store, renderer host, and frontend host SDK were added. The move affects routing, overview tabs, modal rendering, preview rendering, chat slash commands, and recovery/reset flows.
Files/endpoints/components involved: `frontend/src/plugins/appSubsystem.ts`, `frontend/src/plugins/appSubsystemFrontendHost.ts`, `frontend/src/plugins/appSubsystemRendererHost.tsx`, `frontend/src/plugins/runtime.ts`, `frontend/src/plugins/runtimeInternal.ts`, `frontend/src/components/Pages/router.tsx`, `frontend/src/components/Panes/Overview/Overview.tsx`, `frontend/src/components/Pages/MainContainerCore.tsx`, `frontend/src/components/Modals/ModalContainer.tsx`, `frontend/src/components/AppHeader/FileMenu.tsx`, `plugins/setta-json-render-app-gen/frontend/src/index.ts`. Host-owned `frontend/src/components/Pages/App/AppMainContainer.tsx`, `frontend/src/components/Pages/App/AppWrapper.tsx`, `frontend/src/components/Pages/Project/AppPreview.tsx`, and `frontend/src/components/Modals/AppDeploymentsModal/PublishAppDeploymentModal.tsx` were removed from the host tree and rehomed into the plugin frontend.
Default-value changes, moved/renamed UX flows, or relocated logic: the Overview app tab title/quick-info/more-menu label are now provider-supplied rather than hardcoded; the `/app` route now shows an explicit "App Mode Unavailable" state when no valid deployment-runtime provider is active; the File menu only shows "Publish App Deployment" when the active provider registers an app deployment modal; app slash commands are plugin-provided rather than coming from a host-local `appGenerationSlashCommands.ts`.
Reviewer guardrail: do not restore direct host ownership of these UI flows or bypass plugin registration by importing plugin source directly. Reviews on follow-up branches should assume the provider registration is the source of truth for app authoring UI, preview UI, app route UI, modal UI, and app chat affordances.

**4. App deployment publishing now packages the active provider plugin into the deployment and app startup is provider-aware**
What changed: before this branch, publishing an app deployment only wrote deployment content and app startup mostly validated the manifest type. After this branch, publishing an app deployment also copies the active provider plugin into `deploymentRoot/.setta_plugins/<pluginID>`, writes `plugins_state.json` for that provider, and app startup / `setta app` require a single active provider that declares app deployment runtime support.
Why this appears intentional: a new provider-aware app publish service was introduced, startup now resolves deployment type registrations through app-subsystem runtime capabilities, CLI app mode has a provider preflight, and tests explicitly cover the no-provider failure case plus unknown plugin IDs.
Files/endpoints/components involved: `internal/appsubsystem/apppublish/service.go`, `internal/appsubsystem/apppublish/content.go`, `internal/plugins/deployment_snapshot.go`, `internal/appsubsystem/deployment_runtime.go`, `internal/appsubsystem/deployment_type_registration.go`, `cmd/setta-server/startup.go`, `cmd/setta-server/startup_test.go`, `internal/settacmd/app.go`, `internal/deployments/type_registry.go`, `internal/app/deployment_type_registry.go`.
Default-value changes, moved/renamed UX flows, or relocated logic: app startup output is now resolved through deployment type registration metadata instead of a hardcoded app deployment spec; when provider requirements are not met, app mode fails before launch with explicit provider-selection errors; deployment plugin config is remapped to workspace scope for packaged deployments.
Reviewer guardrail: do not remove the packaged provider plugin/state from app deployments, and do not weaken app startup back to "manifest type only" validation. This branch intentionally makes deployed app mode depend on the packaged provider runtime.

**5. The first-party JSON-render app subsystem became a real runtime-managed plugin package, and the host now ships plugin-runtime SDK helpers**
What changed: before this branch, the first-party app plugin was not yet a real runtime-managed package surface. After this branch, `plugins/setta-json-render-app-gen` contains a real plugin manifest, frontend source/build path that produces the packaged frontend bundle, runtime backend, wheel packaging, and a plugin-facing frontend SDK contract; the main Python package now also ships `setta.plugin_runtime` and Go-owned shared constants that installed plugin backends can call.
Why this appears intentional: the repo added a plugin-owned frontend package, a vendored SDK build for staged-source builds, a runtime backend that delegates listener endpoints through local core, Python package manifest changes, and extensive wheel/install tests.
Files/endpoints/components involved: `plugins/setta-json-render-app-gen/setta.plugin.json`, `plugins/setta-json-render-app-gen/runtime_backend/main.py`, `plugins/setta-json-render-app-gen/frontend/package.json`, `plugins/setta-json-render-app-gen/frontend/src/index.ts`, `plugins/setta-json-render-app-gen/frontend/vendor/app-subsystem-frontend-sdk/dist/index.js`, `frontend/plugin-sdk/app-subsystem/*`, `backend/setta/plugin_runtime/__init__.py`, `backend/setta/plugin_runtime/app_subsystem.py`, `backend/setta/plugin_runtime/local_core.py`, `pyproject.toml`, `tests/start/test_packaged_distribution.py`, `tests/plugin_runtime/test_local_core.py`.
Default-value changes, moved/renamed UX flows, or relocated logic: the plugin manifest still intentionally keeps `enabledByDefault: false`; plugin backend listener endpoints are now the contract for app-definition runtime operations; plugin frontend build metadata lives under the plugin's own `frontend/` package rather than the host frontend package. This is standalone in the sense of "standalone as a Setta plugin": the plugin still intentionally depends on explicit Setta host/runtime surfaces (`setta.plugin_runtime`, local-core, and published Setta frontend SDK packages), and this document should not be read as claiming a hostless plugin model.
Reviewer guardrail: do not strip these packaged plugin assets or SDK helpers back out of the distribution, and do not reintroduce repo-path assumptions into the plugin frontend/backend build. A standalone Setta plugin may require the Setta runtime and published Setta SDK packages, but its frontend source, tests, build config, and packaged SDK type surface must not import repo-local host frontend aliases such as `state/*`, `utils/*`, `openapi/*`, `components/*`, `plugins/*`, `testUtils/*`, or `frontend/src/*`. Do not fix clean-checkout plugin packaging by unignoring or committing generated frontend bundles such as `frontend/dist/*`; the plugin package/wheel path must produce those artifacts from tracked plugin-owned source and declared dependencies, or tests must run that plugin-owned build before validating manifest assets. Also do not make `frontend/plugin-sdk/app-subsystem` "standalone" by checking in SDK build artifacts or a large generated declaration fanout. The source SDK package should stay source-first and package-owned: package-local source plus package-local generated inputs it truly owns. It must not depend on repo-local host aliases or repo-private generation paths, and it should not require a checked-in `dist/` or a broad checked-in `types/**` tree to count as standalone. This branch is explicitly making the app subsystem shippable as a real plugin within the Setta host/runtime contract. Separately, do not treat the public third-party authoring surface as fully finished just because the runtime is now provider-driven: the checked-in manifest schema/docs still lag some runtime-supported capabilities, so findings about schema/docs mismatch remain valid.

## Bug Fixes

**1. Browser-side rewritten OpenAPI requests now preserve POST bodies and request metadata**
What changed: before this branch, the HTTP OpenAPI client rebuilt rewritten requests with `new Request(resolvedURL, request)`, which could trigger Chromium cross-origin failures and make rewritten POST behavior brittle. After this branch, the client explicitly reconstructs the request, preserving method, headers, credentials, and body bytes while changing only the URL.
Why this appears intentional: the new helper documents the Chromium `ERR_ALPN_NEGOTIATION_FAILED` failure mode directly and adds a focused regression test that checks POST body preservation.
Files/endpoints/components involved: `frontend/src/openapi/http/client.ts`, `frontend/src/openapi/http/client.test.ts`.
Default-value changes, moved/renamed UX flows, or relocated logic: GET/HEAD requests continue to omit a body; non-GET/HEAD requests now clone `arrayBuffer()` explicitly before the URL rewrite.
Reviewer guardrail: do not replace this with the old `new Request(url, request)` pattern unless the browser bug is intentionally re-evaluated. Follow-up branches should preserve the explicit rebuild path for rewritten requests.

**2. App-generation mode handling is now live-registry driven, which preserves historical replay/edit behavior instead of hardcoding a fixed enum**
What changed: before this branch, app-generation mode parsing, prompt construction, and image requirements were hardcoded around a fixed set of host-owned modes. Persisted or replayed app-generation turns could be dropped or misvalidated when the active provider changed, and queued-draft replay used stale slash-command snapshots for app commands. After this branch, the backend uses a live `chatmodes.AppGenerationModeResolver`, persisted mode values are kept as trimmed strings, historical replay/edit is blocked only when the active registry cannot support the saved mode, and queued app slash commands can replay against the current registry.
Why this appears intentional: the mode logic moved into `internal/appsubsystem/chatmodes`, backend services were rewired to use resolvers, frontend replay helpers were updated, and new compatibility/integration tests were added around replay and registry changes.
Files/endpoints/components involved: `internal/chatmodes/app_generation.go`, `internal/app/app_generation_modes.go`, `internal/managedchat/service.go`, `internal/managedchat/service_start_chat.go`, `internal/externalagents/send.go`, `internal/agentruns/app_generation.go`, `frontend/src/components/Panes/Overview/ProjectLevelAI/ProjectChatCore.tsx`, `frontend/src/components/Panes/Overview/ProjectLevelAI/projectChatCoreUtils.ts`, `frontend/src/components/Chat/ChatInput.tsx`, `frontend/src/components/Chat/chatInputHelpers.ts`, `frontend/src/state/utils/chatAppGeneration.ts`, `frontend/tests/e2e/overview/project-ai/project-ai-chat-queued-current-registry-replay.spec.ts`.
Default-value changes, moved/renamed UX flows, or relocated logic: `plain_chat` is now the explicit serialized fallback for non-app-generation turns; app chat custom-mode defaults now come from `AppSubsystemChatUIConfig` rather than `ProjectChatUIConfig`; image-required status comes from provider registration (`imageRequiredModes` / `requiresImageAttachment`) rather than a hardcoded `json_render_with_image` check.
Reviewer guardrail: do not reintroduce hardcoded host enums or hardcoded image-mode logic in host code. Preserve the live resolver and provider-driven replay behavior, even if it feels more indirect.

**3. App subsystem provider resolution now fails closed for disabled, invalid, and conflicting providers**
What changed: before this branch, the runtime did not expose first-class app-subsystem selection status and could not clearly represent "provider exists but is invalid", "provider is disabled", or "multiple providers are active". After this branch, runtime/status payloads include `featureCapabilities.appSubsystem` and explicit selection statuses: `no_provider`, `disabled_provider`, `invalid_provider`, `active`, and `provider_conflict`. Providers that declare app-subsystem features but do not register the required backend contract are treated as invalid instead of being accepted.
Why this appears intentional: provider-selection data structures, runtime/status payload changes, backend probe contract validation, startup/CLI failures, frontend unavailable messages, and a large test matrix were all added together.
Files/endpoints/components involved: `internal/plugins/backend_probe.go`, `internal/plugins/discovery.go`, `internal/plugins/runtime.go`, `internal/plugins/status.go`, `frontend/src/plugins/appSubsystem.ts`, `internal/appsubsystem/deployment_runtime.go`, `cmd/setta-server/startup.go`, `internal/settacmd/app.go`, `tests/fixtures/plugins/app-subsystem-unknown-id/*`, `internal/plugins/runtime_test.go`.
Default-value changes, moved/renamed UX flows, or relocated logic: app-mode unavailable messages now explicitly mention disabled providers, invalid providers, conflicting providers, or a selected provider that lacks deployment runtime; the startup error message for app mode now includes the exact provider failure reason.
Reviewer guardrail: do not "pick one anyway" when multiple providers are active, and do not ignore missing backend-contract registration. The fail-closed behavior is a deliberate safety change.

**4. Plugin runtime refresh now rebuilds app HTTP handler state atomically when app-subsystem capabilities change**
What changed: before this branch, plugin runtime refresh could replace backend tools and language servers without also rebuilding the app HTTP handler / publish-service wiring that depends on current app-subsystem capabilities. After this branch, the refresher tracks app-subsystem capabilities, swaps runtime tools, refreshes the swappable app handler, and rolls both runtime/tooling and capabilities back together if the handler refresh fails.
Why this appears intentional: new capability state, refreshable handler plumbing, and rollback logic were added specifically around plugin runtime refresh, with dedicated tests for refresh success and rollback.
Files/endpoints/components involved: `internal/app/plugin_backend_runtime_refresh.go`, `internal/app/app_handler_refresh.go`, `internal/app/app_subsystem_capabilities.go`, `internal/app/app.go`, `internal/app/plugin_backend_runtime_refresh_test.go`.
Default-value changes, moved/renamed UX flows, or relocated logic: current app publish service wiring is now re-derived from live app-subsystem capabilities and current active provider snapshot instead of being effectively static after startup.
Reviewer guardrail: do not remove the handler refresh/rollback path when touching plugin refresh code. Follow-up branches should preserve the atomic refresh behavior for app-subsystem capability changes.

**5. Host-side app state updates now queue through the loaded app-subsystem controller instead of racing plugin load**
What changed: before this branch, AI tool results, app-spec patch preview streaming, and websocket app-session recovery updated host app stores directly. Once app state moved into the plugin frontend, those direct writes could race provider registration load or mutate the wrong state tree. After this branch, the host routes those operations through `frontend/src/plugins/appSubsystem.ts`, applying them to the loaded controller or queueing them by capability signature until the selected provider frontend is ready.
Why this appears intentional: the old host app-preview streaming module and app state hooks were deleted, new controller methods were added, and host callers were systematically rewritten to use the app-subsystem bridge.
Files/endpoints/components involved: `frontend/src/plugins/appSubsystem.ts`, `frontend/src/plugins/appSubsystemFrontendHost.ts`, `frontend/src/state/actions/ai.ts`, `frontend/src/state/actions/websocketReceive.ts`, `plugins/setta-json-render-app-gen/frontend/src/appSubsystemPreviewController.ts`, `plugins/setta-json-render-app-gen/frontend/src/state/actions/app.ts`, `plugins/setta-json-render-app-gen/frontend/src/state/actions/appProjectState.ts`.
Default-value changes, moved/renamed UX flows, or relocated logic: app-session reset/initialization now goes through a provider-aware frontend host; pending app-spec preview deltas and structured-content mutations are intentionally retained until the selected provider registration finishes loading.
Reviewer guardrail: do not revert to direct host-store writes for plugin-owned app state. Preserve the queued controller bridge even if it looks more verbose.

**6. Unknown/non-first-party app-subsystem provider IDs now work end to end**
What changed: before this branch, multiple surfaces still assumed the first-party provider ID or host-owned implementation details. After this branch, startup, package-manager discovery, deployment snapshots, runtime frontend/backend registration, and packaged-plugin tests all explicitly support an app-subsystem provider with an arbitrary plugin ID.
Why this appears intentional: the repo adds an `app-subsystem-unknown-id` fixture plugin, provider-neutral generator work, package-manager/runtime tests, and startup tests proving parity with a non-first-party ID.
Files/endpoints/components involved: `tests/fixtures/plugins/app-subsystem-unknown-id/*`, `internal/plugins/runtime_test.go`, `cmd/setta-server/startup_test.go`, `tests/plugin_runtime/test_plugin_backend_guardrails.py`, `internal/appsubsystemproviders/providers.go`, `cmd/setta-gen-go-type-registries/main.go`, `cmd/setta-gen-http-openapi/main.go`.
Default-value changes, moved/renamed UX flows, or relocated logic: provider-specific frontend assets and runtime endpoints are now selected by the active plugin ID rather than by a hardcoded first-party ID.
Reviewer guardrail: do not reintroduce first-party-ID assumptions when touching app-subsystem logic, generated values, or startup/deployment code.

## Intentional Behavior Changes To Preserve

**1. Host/plugin import and build boundaries are now actively enforced**
What changed: before this branch, it was still easy for host frontend code to import plugin frontend source directly, for plugin frontend code or tests to reach back into host aliases, or for plugin builds to depend on repo-root package layout. After this branch, the repo adds explicit boundary checks so host runtime code must load plugin frontend through runtime metadata, plugin frontend tests and source must use plugin-owned code or the published SDK, and plugin-owned builds stay rooted inside the plugin tree.
Why this appears intentional: the branch adds a dedicated boundary checker, Vitest guardrails, a Go host import guard, Python backend guardrails, and wires the checker into `check_quality.sh`.
Files/endpoints/components involved: `frontend/scripts/check_import_boundaries.mjs`, `check_quality.sh`, `frontend/src/plugins/importBoundaryGuardrails.test.ts`, `frontend/src/plugins/appSubsystemBuildBoundaryGuardrails.test.ts`, `internal/appsubsystem/host_import_guard_test.go`, `tests/plugin_runtime/test_plugin_backend_guardrails.py`, `frontend/vite.config.ts`, `plugins/setta-json-render-app-gen/frontend/vite.config.mjs`, `frontend/scripts/buildAppSubsystemPluginFrontend.mjs`.
Default-value changes, moved/renamed UX flows, or relocated logic: the repo wrapper script now deliberately delegates to the plugin-owned frontend build instead of building plugin code from host config; plugin frontend package resolution is intentionally limited to registry dependencies plus the vendored SDK copy.
Reviewer guardrail: do not bypass these boundaries by importing plugin source from the host, importing host aliases from the plugin frontend source or tests, publishing SDK types that resolve through host aliases, or restoring repo-root build assumptions. Also do not satisfy the standalone-SDK goal by checking in SDK build artifacts or a large generated declaration fanout under `frontend/plugin-sdk/app-subsystem`; keep that source package source-first and package-owned, with only the package-local generated inputs it truly owns. Those shortcuts would undo the main architectural point of the branch.

**2. Generated OpenAPI, sidecar metadata, and exported frontend values are now provider-neutral and plugin-aware**
What changed: before this branch, app-related generated surfaces were still centered on host-owned `projectstate` app types and could bake in first-party assumptions. After this branch, generators discover plugin app-definition packages and provider manifests, merge provider capabilities into a neutral OpenAPI-registration build, expose new provider/runtime capability types, and export provider-owned frontend values like `AppSubsystemChatUIConfig`.
Why this appears intentional: generator code, sidecar schema/value generation, OpenAPI builder hooks, and generated artifacts were all updated together. The OpenAPI builder now composes app routes from merged provider capability declarations rather than a hardcoded host app surface.
Files/endpoints/components involved: `cmd/setta-gen-go-type-registries/main.go`, `cmd/setta-gen-http-openapi/main.go`, `internal/appsubsystemproviders/providers.go`, `internal/appsubsystemproviders/discovered_providers_gen.go`, `internal/sharedtypes/sidecar.go`, `internal/frontendbindings/semantic_sidecar.go`, `internal/sharedvalueexports/discovered_value_exports_gen.go`, `internal/appsubsystem/frontendvalues/frontend_value_exports.go`, `frontend/generation/http_openapi/openapi.json`, `frontend/generation/non_http_shared/openapi.json`, `frontend/generation/non_http_shared/schema.json`, `frontend/generation/non_http_shared/sidecar.json`.
Default-value changes, moved/renamed UX flows, or relocated logic: `ProjectChatUIConfig` no longer owns app custom slash-command defaults; those defaults now come from exported `AppSubsystemChatUIConfig`; generated exported values may use a sanitized declaration name while preserving the original provider-scoped export name. Reviewer note: this generator/runtime work moved faster than the checked-in public manifest schema and authoring docs, so the branch should be read as "runtime/provider surfaces are now plugin-aware," not "every public authoring declaration is already fully generalized."
Reviewer guardrail: do not paper over missing generated surfaces with handwritten host-side mirrors or hardcoded first-party provider IDs. Extend the provider-aware generators instead.

**3. App-related MCP tools, UI settings, and route registration are intentionally contributed extensions, not core defaults**
What changed: before this branch, the core MCP server, core UI-setting registry, and frontend route registration types directly knew about app tools/settings/routes. After this branch, app surfaces are contributed via builder hooks and runtime capability checks: `ContributedToolRegistrations`, `ContributedUISettingBuilders`, and `FrontendAPIRouteRegistrations`.
Why this appears intentional: host defaults were deleted or simplified while contributed builders were added to `mcpx`, `uisettings`, and `httpapi`, and the app subsystem now plugs into those extension points instead of living in the default core lists.
Files/endpoints/components involved: `internal/mcpx/server.go`, `internal/mcpx/ui_setting_tools.go`, `internal/httpapi/frontend_route_registrations.go`, `internal/appsubsystem/mcptools/registrations.go`, `internal/appsubsystem/appuisettings/entries.go`, `internal/httpapi/openapi_document_builder.go`.
Default-value changes, moved/renamed UX flows, or relocated logic: `core.app.*` settings are no longer defined in the core UI registry; app MCP tools are no longer in the default tool list; app route registration is now a contribution set rather than a hardcoded field bundle.
Reviewer guardrail: do not move these app-specific contributions back into unconditional core registries for convenience. Preserve the contributed-extension shape so future providers can continue to swap in cleanly.
